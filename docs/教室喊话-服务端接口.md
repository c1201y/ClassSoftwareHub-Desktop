# 教室喊话 · 服务端「配对登记」接口（待实现）

> 状态：**客户端已按此协议实现，服务端待实现**。桌面端遇到 404 或不可达时按「服务端不支持」降级处理，
> 不会报错也不会卡住功能 —— 只是跨网络时看不到「谁保存了本机配对码」。
>
> 背景：桌面端需要知道「哪些电脑保存了本机配对码」，并能主动移除（防滥用）。
> 同一局域网内已经由客户端之间直连 HTTP 解决（`POST /bind`、`POST /unbind` 走对端 47821 端口）；
> **不在同一网段时必须由服务端中转**，因此需要新增下面三个端点。

## 一、现有端点（已上线，本次不改）

| 端点 | 说明 |
|---|---|
| `POST /api/announce/send` | 发喊话。body `{pairCode, text, from, duration}` → `{ok, devices, skipped}`；错误 `403 no_device`、`429 rate_limited` |
| `GET /api/announce/poll?deviceId&pairCode&name` | 教室机轮询取件。204 无消息 / 200 带消息体 |
| `GET /api/announce/list?pairCode` | 查该码下登记的设备。**注意语义**：这是「用这个码在轮询的设备」，也就是码的主人，不是保存过它的发送端 |

`gate:ann:d:<pairCode>` 这张注册表就是「码的主人」，下面的权限校验要用到它。

## 二、新增 ① `POST /api/announce/bind`

发送端保存了一台电脑的配对码之后调用，向该码的主人登记自己。

**请求**

```json
{ "pairCode": "349533", "senderId": "11bfb8bd2134d94a", "name": "DESKTOP-ABC", "label": "高28班" }
```

| 字段 | 类型 | 约束 |
|---|---|---|
| `pairCode` | string | 6 位数字 |
| `senderId` | string | 16 位十六进制（发送端的设备指纹，客户端已固定此格式） |
| `name` | string | ≤ 64 字符，可空 |
| `label` | string | ≤ 24 字符，可空 |

**响应**：`200 {"ok":true}`

**错误**：`400 bad_request`（字段不合法）、`403 unknown_pair`（该码当前没有任何设备在轮询 → 视为无效码）

**存储**：键 `gate:ann:b:<pairCode>`，值形如

```json
{ "11bfb8bd2134d94a": { "name": "DESKTOP-ABC", "label": "高28班", "ts": 1761350000 } }
```

同一 `senderId` 重复 bind 视为更新（覆盖 name/label/ts，并清除 `revoked` 标记）。建议保留 90 天后惰性清理。

## 三、新增 ② `GET /api/announce/binders?pairCode=<code>&deviceId=<本机指纹>`

接收端打开页面时拉取「谁保存了本机配对码」。

**响应**：`200`

```json
{ "ok": true, "binders": [ { "id": "11bfb8bd2134d94a", "name": "DESKTOP-ABC", "label": "高28班", "ts": 1761350000 } ] }
```

按 `ts` 倒序，最多返回 50 条。

**错误**：`403 forbidden` —— `deviceId` 不是该码的主人（校验方式：`deviceId` 在 `gate:ann:d:<pairCode>` 里）。这一条很重要：否则任何人拿到码就能看到「谁在用它」。

## 四、新增 ③ `POST /api/announce/unbind`

接收端删除登记时调用。

**请求**

```json
{ "pairCode": "349533", "deviceId": "本机指纹", "senderId": "11bfb8bd2134d94a" }
```

- 带 `senderId`：只移除这一条（接收端删单条）
- 不带 `senderId`：清空该码下全部登记（接收端「全部清空」）

**响应**：`200 {"ok":true,"removed":1}`

**错误**：`403 forbidden`（`deviceId` 不是码主）、`400 bad_request`

## 五、与 `send` 的联动（关键）

删掉登记后，发送端本地还留着这个码 —— 必须有个反向信号它才能知道。

**约定**：`send` 时若发送端在 `gate:ann:b:<pairCode>` 里被标记为 `revoked`，返回

```
403 {"error":"revoked"}
```

客户端收到后会把本地「已保存的电脑」里那条删掉并提示用户。

**实现建议**：`unbind` 不要物理删除，而是打标记 `{ "revoked": true, "ts": ... }` 保留 30 天；
期间该 senderId 再 `send` → `403 revoked`；30 天后连同记录一起清掉。
（发送端重新 `bind` 时清除该标记 —— 说明用户又主动保存了。）

## 六、客户端行为（已实现，供对照）

| 时机 | 客户端做什么 |
|---|---|
| 保存设备 | 对方在同一局域网 → 直连对端 `POST /bind`；否则 → 调服务端 `POST /api/announce/bind` |
| 打开接收页 | `GET /api/announce/binders`，与本地局域网登记记录合并展示（按机器名去重） |
| 删除 / 全部清空 | 局域网可达就直连对端 `/unbind`，不可达就调服务端 `POST /api/announce/unbind` |
| 发送时 | 收到 `403 revoked` → 移除本地「已保存的电脑」那条，提示「对方已删除你的登记」 |

## 七、兼容性

- 老版本客户端不会调用这三个端点，行为完全不变。
- 新客户端遇到 `404` / 网络不可达 → 按「服务端不支持」处理：只用局域网通道，界面不报错。
- 三个端点都不涉及用户账号体系，鉴权沿用现有「配对码 + 设备指纹」的信任模型，与 `poll` 一致。
