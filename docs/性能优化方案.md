# 性能与动画流畅性方案（dv1.1.0-insider1.3）

> 起因：2026-10-01 「功能丰富但部分页面跳转还是有卡卡的感觉」。本版把重心放在**性能与动画流畅性**上。
> 本文件记录四件事：**怎么量 → 量到什么 → 改了什么 → 什么判定不改 / 还剩什么**。
> 相关代码：`Core/PerfLog.cs`（探针）、`Services/MemoryTrimmer.cs`、`Pages/ShellPage.xaml(.cs)`、各页 XAML 的 `NavigationCacheMode`。

---

## 一、怎么量：`Core/PerfLog.cs`

手感不能当验收依据，所以先装探针。它把每次切页拆成两段写进
`%LOCALAPPDATA%\ClassSoftwareHub\perf.log`：

| 字段 | 含义 |
|---|---|
| **构造+解析** | `Frame.Navigating` → `Frame.Navigated`：页面实例化 + XAML 解析 + `OnNavigatedTo` |
| **到首帧** | `Navigated` → 下一次 `CompositionTarget.Rendering`：真画到屏幕上 |

开关：**Debug 编译默认开**；正式版默认关，要开就设环境变量 `CSH_PERF=1`。
窗口被收进托盘 / 最小化时 `Rendering` 不回调，所以带 2 秒超时兜底，不会把帧回调漏在树上。

其他用法：`PerfLog.Mark("...")` 记任意里程碑；`using (PerfLog.Scope("加载软件清单")) { ... }` 记代码块。

**怎么读**：

```bash
cat "$LOCALAPPDATA/ClassSoftwareHub/perf.log"
```

排障单页可以 `ClassSoftwareHub.exe --page=<tag> --minimized` 直接落页。

## 二、量到了什么

一轮真实切页（应用已启动、不是冷启动）实测：

| 切到 | 构造+解析 | 到首帧 | 判断 |
|---|---|---|---|
| 软件下载 `SoftwarePage` | 13 ms | **225 ms** | 🔴 首屏最贵 |
| 虚拟键盘 `VirtualKeyboardPage` | 52 ms | **198 ms** | 🔴 重 |
| 提交软件 `SubmitPage` | 23 ms | **130 ms** | 🟠 偏重 |
| 侧边布局 `SidebarLayoutPage` | 8 ms | **83 ms** | 🟠 |
| 反馈中心 / 实验性 / 内置工具 | 3–8 ms | 38–44 ms | 🟢 无感 |
| 任务进行 / 更新日志 / 首页 | 4–18 ms | 23–32 ms | 🟢 |
| 本机核实（首次 → 二次） | 14 → 3 ms | 40 → 17 ms | 🟢 便宜 |

**结论一：页面构造与 XAML 解析本身很便宜（3–96 ms）"切页卡"的主因不在这里。**
贵的是首帧那一段（网格容器实化、图标加载），以及原来挂在切页路径上的内存回收。

**结论二（真正的元凶）：每次切页停稳 3 秒后，在 UI 线程上做一次全量 GC + `EmptyWorkingSet`。**

```
Pages/ShellPage.xaml.cs  ContentFrame.Navigated → MemoryTrimmer.TrimLater(3000)
Services/MemoryTrimmer.cs  GC.Collect(2) → GC.WaitForPendingFinalizers()【阻塞】→ GC.Collect(2) → EmptyWorkingSet()
```

三重伤害：① `WaitForPendingFinalizers` 直接卡住 UI 线程；② 回收把工作集还给系统，紧接着用户滚动时
每一页都要重新缺页；③ 3 秒的定时器恰好落在用户"切过去、刚开始滚动/点击"的瞬间。
节流是 4 秒，所以连续浏览时基本每 4 秒挨一次。

## 三、本版改了什么

### 1. 内存回收彻底移出切页路径（最要紧的一条）

- `ShellPage` 的 `Navigated` 里**删掉** `MemoryTrimmer.TrimLater(3000)`，换成探针挂钩。
- `MemoryTrimmer` 新增闸门 `IsIdle`：由 `MainWindow` 注入，**只有"窗口用户看不见"（收进托盘 / 最小化）才真回收**，
  看得见时一律直接返回。`force:true`（用户主动触发）不受限。
- 回收本体挪到**后台线程**执行（GC / `EmptyWorkingSet` 都不需要 UI 线程）。
- 触发点改为：`HideToTray()`（原有）+ **最小化时**（`_appWindow.Changed` 里新加，延时 2.5s，还原回来就自动跳过 —— 因为闸门会在触发时重新判定）。

效果：用户看得见窗口的时候，进程**不再做任何主动的内存回收**。

### 2. 页面缓存 + 列表不重建

- `Pages/ShellPage.xaml`：`Frame.CacheSize` 由 `0` 改成 `12`。
- 常用 8 页 XAML：`NavigationCacheMode` 由 `Disabled` 改成 `Enabled` ——
  `WelcomePage` / `SoftwarePage` / `ToolsPage` / `SettingsPage` / `DownloadsPage` / `ChangelogPage` / `ExperimentalPage` / `MachineCheckPage`。
  其余（详情页、提交软件、侧边布局、三个专杀页、虚拟键盘、工具子页）保持 `Disabled`：它们要么带表单/拖拽/定时器状态，要么本来就便宜。
- `SoftwarePage`：`OnNavigatedTo` 加**状态指纹**（分类｜关键词｜视图｜内容包版本｜内容来源）。
  指纹没变就跳过重建。**这一步是关键** —— 该页 `Apply()` 每次都把 `ItemsSource` 换成新的 `List`，
  GridView 见到新集合会把**所有卡片容器（含图标）整个重建**，不跳过的话"缓存了"也照样花掉那 200ms。

### 3. 切页过渡动画（原生）

`ContentFrame.ContentTransitions` 加了 WinUI 原生的
`NavigationThemeTransition` + `EntranceNavigationTransitionInfo`（淡入 + 轻微上移）。
**不是自绘动画**，是框架自带的那套 —— 与「能用系统控件就用系统控件」一致。
以前一次过渡都没有，页面是"啪"地硬切，构建耗时裸奔暴露；现在至少观感上是连续的。

### 4. 背板默认从亚克力改成云母

`AppSettings.Backdrop` 默认值 `acrylic` → `mica`（`MainWindow.ApplyBackdrop` 的空值兜底同步改）。
- 亚克力要**每帧实时模糊**窗口背后，滚动/拖拽时是白交的 GPU 税；云母只采样一次壁纸，几乎零成本。
- 云母本就是 Windows 11 系统窗口（设置、资源管理器）用的材质，更贴"要 Windows 原生"这条铁律。
- Windows 10 上云母不可用 → `ApplyBackdrop` 已会自动退到亚克力，不用额外判。
- ⚠️ **只影响没存过设置的新用户**；老用户存档里存的是自己选的值，不会被改。设置页三个选项都没变。

### 5. 首页

- `SystemInfo.Gather()`（注册表 + SMBIOS + 显示适配器一串读取）原来在 `Loaded` 里同步跑，
  现在挪到后台线程算完再填，首屏不再先僵一下。
- 首页 banner 加了 `DecodePixelHeight = 280`（图是 1512×720，只按高度 140 显示）——
  以前是整张全尺寸解码（约 4MB 位图）再缩下去。

## 四、审阅后**判定不改**的

**`Pages/SidebarLayoutPage.xaml.cs` 的拖拽补间**（`Height` 的 `Storyboard` + `CompositionTarget.Rendering` 手写逐帧位移）。

我原本把它列为"该转合成层"的候选，读了文件里的原始注释后改判：那套写法是**刻意的**，理由已写在代码里 ——
让位动画的自变量是"位移有没有到达自身高度"，用 `TranslateTransform` 把一行挪到"整个离开它自己的格子"时，
**整行会不重画**（视觉上消失），而 `Margin` 是布局属性，走的是必然重画的路径。`Height` / `Opacity` 的
Storyboard 动画本身是会重画的，不用动。**动它风险大于收益，保持现状。**

## 五、还没做 / 后续候选

| 项 | 说明 | 优先级 |
|---|---|---|
| 工具子页缓存 | `ClockToolPage` 等 6 个工具页仍 `Disabled`。它们有各自动态状态，要先逐页确认"缓存后状态不会串"再开 | 中 |
| `SubmitPage` 130ms | 表单页首帧偏重，可以先看看是不是模板/图片，再决定 | 中 |
| `DetailPage` | 每进一次是一个新实例（文档注释里提到过泄漏路径），是否值得缓存要先评审 | 中 |
| 剩余 4 处 `{Binding}` | 反射绑定（`SettingsPage` / `WelcomePage` / `RosterEditorDialog`），量很小 | 低 |
| 大清单虚拟化 | 内容包条目多了以后 `GridView` 一次性实化的问题，当前数量还好 | 低 |
| 冷启动 350–600ms 首帧 | 这是整个应用第一帧（含 Window 创建 + 背板挂载），属于下一步的事 | 低 |

## 六、本版验证

- 编译：`dotnet build -c Debug` → **0 错误 / 4 个既有警告**。
- 冒烟：15 个页面（含 `--page=feedback-form`）逐个 `--page=<tag> --minimized` 启动，
  **`crash.log` 零新增**（32876 → 32876 字节）。
  → 说明缓存、过渡、背板默认、异步首页这几处改动都不会让页面打不开。

## 七、待手测（我量不了，得人来感受）

1. 依次点遍导航（尤其**软件下载 / 虚拟键盘 / 提交软件 / 侧边布局**），确认"切页顿一下"是否消失；
2. **同页进出复现**：`软件下载` → `内置工具` → `软件下载`，第二次应该是**瞬开**（缓存 + 指纹生效）；
3. 切页过渡动画是否与整体观感协调（`EntranceNavigationTransitionInfo`，淡入 + 轻微上移）；
4. 背板默认变成云母后，浅色/深色下是否可接受（**不满意改回亚克力只需在设置页选一下**）；
5. 长时间使用后内存是否仍然受控（回收现在只在收进托盘 / 最小化时做）。
